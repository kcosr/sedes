# Pi isolated workspace sandbox contract

This document records the implemented isolation, ownership, lifecycle, and
verification contract for Pi threads that use an isolated local workspace. For
operator setup and user-visible behavior, see the Pi backend and user guides.

## Supported scope

The current implementation supports only a Pi target on the Local execution
environment. Codex,
Claude, Grok, Pi on SSH, automations that cannot reproduce the same allocation,
managed terminals, the Sedes agent-tool CLI, and model-invokable provider
extensions or tools outside the closed workspace set are intentionally
unsupported and must fail closed. There is no unsandboxed fallback.

The closed workspace tool set is `bash`, `read`, `write`, `edit`, `grep`,
`find`, and `ls`. Every workspace invocation uses the allocation's sandbox
executor. Thread-enabled Sedes application agent tools may also use Pi's
Native Progressive or Individual mode, but execute only through the
existing scoped Sedes facade and authentication. They do not become
workspace filesystem or shell implementations. New SDK tools, project
extensions, skills, prompt templates, arbitrary custom tools, and the Sedes
CLI do not inherit authority merely because Pi discovers or recognizes them.

## Ownership and authority

The operator owns the installation policy that enables Bubblewrap and admits
network profiles. The application principal owns workspaces and threads. One
allocation belongs to exactly one server-derived tenant, principal, execution
environment, source workspace, and Sedes thread. The browser may select an
admitted preference but never supplies those scope identifiers or a host path
as authority.

The allocation record persists an opaque identity, its exact scope, network
profile, lifecycle state, and environment-native paths. Runtime keys include
the complete scope and allocation generation. A workspace path, clone path, or
provider conversation id is not an allocation identity.

An allocation lives beneath one installation-owned state root with restrictive
permissions. Each child name is generated by Sedes and resolved beneath that
root. Creation, open, import, and deletion reject symlinks, path replacement,
scope mismatch, and any target that cannot be revalidated. Cleanup acts only on
the exact validated allocation child; it never recursively targets a configured
root, user home, workspace root, or unresolved path.

## Threat model

Repository content, model output, and commands executed by workspace tools are
untrusted. They may attempt arbitrary code execution, traversal through
symlinks, process escape, credential discovery, socket access, network access,
or modification of the source checkout. The sandbox protects the Sedes host,
the source workspace, other allocations, and host credentials from that code.
It does not protect a private clone or writable allocation home from its own
agent, and it does not make an `execution-host` network trustworthy.

Except when the thread explicitly selects the exact source as a read-only
mount, the allocation must not expose the original workspace. It must never
expose the host home, Sedes state or configuration, SSH agent, Docker or
Podman socket, display sockets, session
or system buses, unrelated `/run` content, ambient credentials, or host process
namespace. In the `isolated` profile it must not expose the execution host's
network namespace. In the explicit `execution-host` profile, host networking,
including loopback services, is intentionally reachable and must be presented
as the broader authority.

The implementation assumes the source workspace was admitted through Sedes's local
workspace policy. Clone preparation still avoids executing a shell and must not
run repository-controlled checkout filters or hooks with host authority.

## Allocation and workspace access

Each allocation persists one closed workspace-access mode. A `writable_clone`
creates the independent Git clone described below. A `read_only` allocation
creates a private writable home and an empty workspace mountpoint; Bubblewrap
overlays the exact source workspace read-only at `~/workspace`. The read-only
source is a live view and is never an allocation deletion target. Bash and
structured mutators can write elsewhere in the private home and `/tmp`; writes
that cross into `~/workspace` fail at the read-only mount.

For `writable_clone`, Sedes creates an independent clone, not a linked
worktree and not a bind mount of the source workspace. A local clone must use
`--no-hardlinks`; otherwise Git
may share object-file inodes with the source repository. Submodules are not
recursively initialized. Clone commands are constructed as an executable plus
an argument vector, with cancellation and bounded output, never as shell text.

To keep repository-controlled checkout behavior out of the host boundary,
clone preparation should create the object database without a checkout and
perform the checkout within the same restricted preparation boundary used by
the worker. If the implementation instead proves that its selected Git path
cannot execute repository-controlled or host-global filters and hooks, that
proof and a regression test are required. Failure or cancellation removes only
the incomplete allocation after exact-target revalidation.

The private home appears inside the sandbox as `/home/agent`, the effective
workspace as `/home/agent/workspace`, and Pi starts in `/home/agent` for both
access modes. Relative Bash and structured file-tool paths resolve from home;
project paths therefore begin with `workspace/`, while absolute sandbox paths
remain usable. Project context discovery remains rooted at the workspace. The
allocation home, clone when present, and Pi-owned state persist when a worker
stops or Sedes restarts.

Git commits retain their normal object identities. Handoff imports a committed
branch by fetching the allocation clone into the source repository, then may
create an ordinary source-repository worktree. Sedes does not convert the
clone directory in place into a linked worktree. Uncommitted and untracked
files are not transferred by Git fetch.

## Bubblewrap boundary

Startup or allocation preparation proves that the configured Bubblewrap binary
and required namespace behavior are available. Missing Bubblewrap, a failed
probe, a launch or handshake error, worker death, malformed protocol traffic,
or an unsupported operation makes the sandbox unavailable. None may select a
local filesystem or shell implementation as recovery.

The worker is launched with a fresh user, PID, IPC, UTS, cgroup, and—except for
the explicit `execution-host` profile—network namespace. The invocation uses
the equivalents of `--unshare-all`, explicit `--unshare-user`, `--disable-userns`,
`--assert-userns-disabled`, `--die-with-parent`, and `--new-session`;
`execution-host` adds `--share-net`. The assertion is required so a kernel that
cannot enforce the nested-user-namespace restriction fails closed. Isolation
does not use best-effort `*-try` flags.

The mount table is an allowlist:

- the allocation home is mounted writable at `/home/agent`; both modes mount
  their project explicitly at `/home/agent/workspace`, using a writable bind
  for the clone and a read-only bind for the exact source;
- required runtime binaries and libraries are mounted read-only at their
  semantic paths;
- `/proc` belongs to the new PID namespace, `/dev` is a minimal Bubblewrap
  device filesystem, and `/tmp` is a fresh tmpfs;
- DNS and CA material needed by `execution-host` networking is selected
  explicitly rather than admitting the host root or all of `/etc`;
- outside the explicit exact read-only workspace bind, the source workspace,
  host home, broad host root, unrelated state, and authority-bearing sockets
  are never mounted.

Bubblewrap clears the environment and sets only reviewed values such as
`HOME=/home/agent`, working directory `/home/agent`, a fixed `PATH`, and bounded
identity/locale values. It does not forward provider tokens, Git credential
selectors, `SSH_AUTH_SOCK`, environment injection hooks, or desktop/session
variables. Protocol handles use explicit standard-I/O or inherited-descriptor
allowlists; opaque capabilities are not placed in command arguments.

## Worker protocol and lifecycle

One active thread attachment owns one worker generation. Requests and responses
use a closed, bounded protocol with exact operation names, schemas, correlation,
and output limits. Unknown operations are denied before dispatch. A response
from an old generation cannot complete a request in a new generation.

Cancellation stops accepting work, rejects pending requests, and kills the
entire owned process group so descendant commands cannot survive. Shutdown uses
a bounded graceful interval followed by `SIGKILL`. A lost or cancelled mutating
operation whose completion cannot be proved has an unknown outcome and is not
automatically replayed. Normal worker disposal preserves the allocation.

Archive keeps the allocation by default. Clone deletion first reports
uncommitted and untracked changes and commits not known to be reachable from a
configured remote. Read-only deletion states that the source is retained and
only the private home and its data are removed. The user may confirm
deletion, which is durable and retryable. A failed deletion remains visible as
requiring cleanup; it is never reported as successful or broadened to another
path.

## Verification matrix

| Boundary              | Required evidence                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Workspace isolation   | Clones use `--no-hardlinks` and do not share source inodes; read-only mode mounts the exact source without copying, rejects source writes, keeps the rest of home writable, and deletes only its allocation.                                                                                                                                                                                                                                                   |
| Scope                 | Wrong tenant, principal, environment, workspace, thread, generation, traversal, symlink, and root-replacement cases are denied.                                                                                                                                                                                                                                                                                                                                |
| Tool authority        | The release-pinned workspace catalog contains exactly seven executor-backed tools (`bash`, `read`, `write`, `edit`, `grep`, `find`, and `ls`); Pi's `powershell` tool is intentionally excluded. Only policy-enabled canonical Sedes application tools may be added through the scoped facade; residual host built-ins, malformed overrides, collisions, newly discovered SDK tools, project resources, arbitrary custom tools, and CLI authority fail closed. |
| Bubblewrap contract   | Argument, mount, environment, and both network-profile tests prove the allowlist and absence of forbidden host paths and variables.                                                                                                                                                                                                                                                                                                                            |
| Failure behavior      | Missing/probe-failed Bubblewrap, launch/handshake failure, malformed protocol, worker crash, and unsupported tools produce no host fallback call.                                                                                                                                                                                                                                                                                                              |
| Lifecycle             | Concurrent attachment is fenced; abort, turn stop, crash, and server shutdown retire the process group and descendants; unknown mutations are not replayed; restart preserves the allocation.                                                                                                                                                                                                                                                                  |
| Real isolation        | Linux Bubblewrap tests prove the common home-starting layout, writable clone behavior, read-only source plus writable home behavior, hidden host paths, both network profiles, and descendant teardown.                                                                                                                                                                                                                                                        |
| Retention and handoff | Keep is the archive default; deletion warnings cover dirty/untracked/unpublished work; exact-target retry and local fetch/worktree import are covered.                                                                                                                                                                                                                                                                                                         |
| Product disposition   | Local Pi advertises support only when all prerequisites hold; Pi SSH and every other compiled backend return explicit unsupported results.                                                                                                                                                                                                                                                                                                                     |

The real Bubblewrap test is a supported-Linux security gate, not a mocked test
or a silent skip. The ordinary typecheck, unit, build, and E2E sequence remains
required. Live Pi verification is separately authorized because it consumes
provider capacity; when omitted, the handoff must say so.
